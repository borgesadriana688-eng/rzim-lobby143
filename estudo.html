1Lógica é a base de tudo

Toda falha de segurança nasce de uma suposição errada na lógica. Antes de pensar em invasão, pense em: o que este código assume que sempre é verdade?

Três blocos que resolvem 90% dos problemas

  • Condição: se (isto) então (aquilo). Erro comum: usar == onde precisava de atenção ao tipo, ou esquecer um caso.
  • Repetição: enquanto (isto) faça. Erro comum: nunca sair do laço, ou sair cedo demais.
  • Acumulador: pegar um resultado e ir somando/filtrando. Erro comum: começar do valor errado.
# conta quantos usuários são admin
admins = 0
for u in usuarios:
    if u.nivel == "admin":
        admins += 1

A falha clássica aqui é confiar em u.nivel vindo do cliente. Se o cliente manda o nível, o atacante manda "admin".

Python e JavaScript

Mesma ideia, duas sintaxes. Aqui você escreve e roda de verdade: JavaScript roda na hora, Python roda no navegador (carrega na primeira execução).

1Lado a lado

Python

def soma(lista):
    total = 0
    for n in lista:
        total += n
    return total

print(soma([1, 2, 3]))

JavaScript

function soma(lista) {
  let total = 0;
  for (const n of lista) {
    total += n;
  }
  return total;
}
console.log(soma([1, 2, 3]));

Diferenças que importam na prática: Python usa indentação para bloco, JS usa chaves. Python é tipagem dinâmica forte, JS converte tipo sozinho ("1" == 1 é verdadeiro, por isso se usa ===).

4Como treinar leitura de código

  1. Leia a função inteira antes de opinar. Nome mente, código não.
  2. Liste o que vem de fora: parâmetro, header, body, banco. Isso é a "superfície de ataque".
  3. Pergunte o que acontece se vier vazio, gigante, com aspas, negativo ou repetido.
  4. Só então procure a falha: onde a suposição quebra.

Esse método vale para ler código de qualquer linguagem. É o mesmo usado em auditoria profissional.

Requisição e banco de dados

Tudo que o app faz vira uma requisição. Tudo que fica salvo vira banco. Entender esses dois é entender a maior parte das falhas reais.

1Anatomia de uma requisição

POST /api/login HTTP/1.1
Host: servidor.com
Content-Type: application/json

{ "email": "eu@email.com", "senha": "123" }
Método
GET lê, POST cria, PUT/PATCH altera, DELETE apaga
Rota
o caminho do recurso, ex: /api/login
Headers
metadados: quem sou eu, que formato, que idioma
Body
o conteúdo enviado (JSON, formulário, binário)
Status
200 ok, 201 criado, 400 errado, 401 sem login, 403 sem permissão, 404 não existe, 500 quebrou

3Banco de dados na prática

Um banco é tabela + linhas + colunas. Este laboratório tem duas tabelas reais: usuarios e mensagens. Escreva SQL e rode.

todos mensagens do 2 ver senhas inserir

Repare: a query "ver senhas" funciona. Em sistema real, senha nunca fica salva assim, fica como hash. Guardar texto puro é uma falha real e comum.

4Por que injeção acontece

Quando o código junta o texto que o usuário digita direto na consulta, o usuário pode reescrever a consulta. Veja os dois lados:

Vulnerável

query = "SELECT * FROM usuarios "
query += "WHERE email = '"
query += email + "'"

O que o usuário digita vira comando.

Correto

cursor.execute(
  "SELECT * FROM usuarios WHERE email = ?",
  (email,)
)

O valor viaja separado do comando.

4Mini CTF: achar a falha no código

O código abaixo é um endpoint nosso de teste. Encontre a falha e escreva a flag no formato MONTROY{...} com a palavra-chave.

@app.route("/api/trocar-senha", methods=["POST"])
def trocar_senha():
    uid = request.json["usuario_id"]
    nova = request.json["nova_senha"]
    db.update("usuarios", {"senha": nova}, {"id": uid})
    return {"ok": True}

A escolha depois da falha

Você achou a falha. Daqui saem dois caminhos, e a habilidade é idêntica nos dois. A diferença é o que você faz com ela.

Caminho 1 · explorar escondido

  • Risco jurídico real: acesso não autorizado é crime, mesmo "só olhando".
  • O dado de outra pessoa vira problema seu.
  • Ninguém confia em quem aparece assim. Não vira carreira.

Caminho 2 · reportar com responsabilidade

  • Programas de bug bounty pagam de centenas a dezenas de milhares de dólares.
  • Você ganha reputação pública e convite pra programas fechados.
  • O sistema fica melhor e você continua convidado a testar.

1Regra que nunca muda

  • Teste só o que é seu, ou o que tem autorização escrita (programa de bounty, contrato, escopo publicado).
  • Ao encontrar falha: pare, registre a prova mínima, avise o dono, não baixe dado de terceiros.
  • Nunca use falha para acesso, cópia, venda ou chantagem.

Aqui no laboratório tudo é ambiente nosso e simulado: nada do que você fizer aqui toca sistema de terceiro.
